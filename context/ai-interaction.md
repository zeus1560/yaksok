# AI 협업 규칙

## 작업 전 필수 확인

`docs/README.md`의 세 가지 규칙을 항상 지킨다.

1. MVP 범위 밖(카카오 로그인, 톡캘린더, 위치·중간지점, 장소 추천·투표 등)은 구현하지 않는다. 요청받으면 범위 외임을 알린다.
2. ❗미결 규칙을 임의로 결정하지 않는다. 구현이 막히면 멈추고 사람에게 묻는다.
3. 문서 간 불일치를 발견하면 `docs/development/DECISION_CONFLICTS.md`를 먼저 확인한다. 이미 있으면 거기 적힌 판단을 따르고, 새 충돌이면 그 파일에 추가하고 알린다.

## 작업 흐름

1. 기능의 범위·근거 규칙 ID·수용 기준을 `context/features/<스펙ID>-<기능명>.md`에 기록한다. 규칙 본문을 옮겨 적지 않고 ID와 문서 경로로 참조한다.
2. `context/current-feature.md`에 스펙 경로, 목표, 검증 계획을 불러온다.
3. 합의된 범위만 구현한다. 구현을 좌우하는 미결 사항은 확인한다.
4. 수용 기준과 결과를 대조하고 테스트·타입 검사·린트·빌드·사용자 흐름을 확인한다.
5. 문제를 고치고 영향받는 검증을 다시 실행한다.
6. 검증 근거를 남기고 완료 이력을 맨 아래에 추가한다.

스펙·기록은 한국어로 쓰고 계획과 실제 구현을 구분한다.

## Git

`docs/architecture/SETUP.md` 4절을 따른다.

- `main`에 직접 커밋·푸시하지 않는다.
- 브랜치 이름은 `<이름>/<타입>-<설명>` 형식이다. 예: `ahn/feat-약속생성-api`, `ahn/fix-투표-중복`. 타입은 `feat`, `fix`, `chore`, `docs` 중 하나다.
- 기능 하나당 브랜치 하나를 만들고 PR로 합친다. 병합된 브랜치는 지우고 다음 기능은 최신 `main`에서 새로 만든다.
- 이름 접두어는 사용자가 알려 준 값을 쓴다. 모르면 묻고, 추측하지 않는다.
- 커밋과 푸시는 사용자가 요청한 경우에만 한다. PR 생성과 병합(`Squash and merge`)은 사람이 한다.
- 커밋 메시지는 `<타입>: <한 줄 요약>` 형식이며 콜론 앞에 공백을 넣지 않는다. AI 공동 작성자 표시를 넣지 않는다.
- 커밋에는 이 기능의 파일만 포함한다. 스키마를 바꿨다면 `prisma/migrations/`의 새 폴더를 반드시 포함한다.
- 기능 변경은 관련 검증이 통과해야 커밋한다.

## 데이터와 운영

- 개발 DB는 각자의 Neon 프로젝트다. 리셋은 본인 개발 DB에서만 허용하며 공유·운영 DB는 리셋하지 않는다.
- 스키마 변경은 마이그레이션으로 남긴다. `prisma db push`는 쓰지 않는다.
- 운영 DB에는 `prisma migrate deploy`만 사용한다.
- `.env`와 실제 연결 문자열을 Git, 문서, 로그, 답변에 남기지 않는다. 환경 변수 점검은 이름만 비교한다.

## 검증과 문제 해결

같은 가정으로 반복 실패하면 원인·오류·다음 조사 방향을 정리한다. 무관한 리팩터링이나 새 기능으로 범위를 넓히지 않는다. 실행한 명령, 결과, 실행하지 못한 항목을 구분한다. 테스트가 없으면 없다고 쓰며 빈 테스트 성공을 만들지 않는다.
