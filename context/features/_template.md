# 기능명

## 식별자와 상태

- 스펙 ID: 파일명과 같은 식별자 (예: `001-erd-schema`)
- 상태: 초안 / 확인 필요 / 대기 / 진행 중 / 검토 중 / 완료
- 문서 작성만으로 구현이나 검증을 완료 처리하지 않는다.

## 근거

규칙 본문을 옮겨 적지 않고 ID와 경로로 참조한다.

- 비즈니스 규칙: 예) TIME-06-01, STATE-05-01 (`docs/specs/rules/`)
- ERD: 예) DATABASE.md 3.3절, 8.2절
- API: 예) TIME-API-01 (`docs/specs/api/time.md`)
- 관련 미결·충돌: `DECISION_CONFLICTS.md`의 ID (예: C-01). 없으면 `없음`

## 선행 작업

선행 스펙 ID와 필요한 이유. 없으면 `없음`. 구현을 막는 미결 규칙은 별도로 적는다.

## 사용자 흐름

시작 조건 → 사용자 행동 → 시스템 처리 → 보이는 결과. 빈 상태·로딩·실패·재시도 포함.

## 수용 기준

각 기준에 근거 규칙 ID를 붙인다.

- [ ] AC-1 (규칙 ID): 주어진 조건에서 사용자가 행동하면 관찰 가능한 결과가 나온다.
- [ ] AC-2 (규칙 ID): 잘못된 입력·권한 없는 요청·잘못된 상태에서의 결과가 정의되어 있다.

## 데이터와 인터페이스

변경하는 테이블·컬럼·제약, 마이그레이션, Route Handler 계약을 필요한 범위만 작성한다. API 명세에 이미 있으면 ID로 참조한다.

## 구현 계획

변경할 파일·모듈과 작업 순서. 변경 이유가 없는 새 라이브러리는 추가하지 않는다.

## 검증 계획

각 수용 기준을 어떤 테스트·명령·브라우저 행동으로 확인할지 적는다. DB 변경은 마이그레이션 검증을 포함한다. DATABASE.md 11절 체크리스트 중 해당 항목을 연결한다.

## 미정 사항

결정할 내용과 이미 합의된 내용을 구분한다.

## 결과

구현 후 수용 기준별 결과와 실제 검증 근거.
