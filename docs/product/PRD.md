# 1. 개요

**제품 이름**

> 약속 잡기 도우미
> 날짜, 시간 조율부터 장소 확정까지, 3인 이상 모임의 약속 잡기 전 과정을 하나의 플로우로 통합하는 카카오톡 챗봇 연동 웹 서비스

**목표**

- 시간 조율과 중간지점 장소 추천 등으로 분리되어 있던 기능을 한 플로우로 통합 (장소는 MVP 이후)
- 카카오톡 챗봇 초대와 링크 공유만으로 **로그인 없이** 참여 가능한 낮은 진입장벽 구조
- **MVP: 약속 생성 → 참여자 등록 → 시간 조율 → 후보 추천 → 방장 확정까지 완결**
- 출발지 기반 중간지점 자동 계산 → 장소 추천 → 투표까지 자동화 (MVP 이후)
- 회원 카카오 간편 로그인 및 톡캘린더 자동 등록 (MVP 이후)
- 목적별(스터디/회식/데이트 등) 큐레이션으로 장소 추천 품질 보완 (MVP 이후)
- 반복 모임 이력 관리를 통한 재사용률 확보 (MVP 이후)

**문제인식**

- "언제"는 카톡 투표, "어디서"는 지도 앱 검색으로 채널이 분산되어 있음
- 3명 이상이 모이면 날짜, 시간 조율만으로도 부담이 크고, 그 이후 장소 문제가 다시 발생함
- 시간 조율 서비스(When2meet, Doodle 등)는 장소 기능이 없고, 장소 추천 서비스(카카오맵, 위밋플레이스 등)는 시간 조율 기능이 없어 통합 서비스가 국내에 공백으로 존재함
- 웹이나 앱을 설치해야 사용 가능하여 접근성이 떨어짐

**→ "날짜, 시간 조율 + 장소 추천 통합 플로우"에 대한 수요가 명확히 존재하지만 접근성이 떨어짐**

# 2. 문제 정의 및 목표

**문제 정의**

- 약속을 잡기 위해 시간 조율(카톡 투표/모두의 시간)과 장소 검색(카카오맵/네이버지도)을 서로 다른 채널에서 반복해야 함
- 참여자가 3명 이상이면 시간 조율 자체의 협의 비용이 커지고, 시간이 정해진 뒤 장소 이슈가 다시 대두됨
- 중간지점 계산은 수동으로 해야 하며, 대중교통 기준 소요시간까지 고려한 정밀 계산 도구는 부족함
- 접근성이 떨어짐

**목표**

- 카카오챗봇을 이용해 링크를 얻어 웹으로 들어오는 사용자 플로우 구현
- 방장이 약속을 생성·설정하고 공유하면, 참여자는 닉네임·PIN으로 등록하고 가능 시간을 입력하는 구조 구현
- 약속 길이 전체를 연속으로 참석 가능한 인원 수 기준으로 시간 후보 자동 계산
- 마감 후 방장이 유효 후보 중 하나를 선택해 일정을 확정하는 플로우 구현
- **MVP는 "약속 생성 → 참여자 등록 → 시간 조율 → 후보 추천 → 방장 확정"까지 완결된 플로우로 완성**
- (MVP 이후) 참여자 출발지 좌표 평균(centroid) 기반 중간지점 계산 및 반경 내 장소 추천
- (MVP 이후) 투표로 장소를 확정하고, 동률 시 방장이 최종 선택권을 갖는 규칙 적용

# 3. 사용자 및 이해관계자

**주요 사용자**

- 대학생 스터디/동아리, 친구 모임, 소규모 회식 등 3인 이상 그룹
- 카톡 투표와 지도 앱을 번갈아 쓰는 데 피로감을 느끼는 모임 주최자(방장)

**이해관계자**

- **외부 API 제공사 :** 카카오 오픈빌더 챗봇(**MVP**) / 카카오 로그인·톡캘린더, 네이버지도(장소 검색·좌표 변환), ODsay(대중교통 소요시간)는 **MVP 이후**

# 4. 기능 요구사항

> ### 핵심 기능 (MVP)
>
> - **참여자 등록**
>   - 닉네임 + 숫자 4자리 PIN으로 약속별 등록. 최초 **등록 완료자**를 방장으로 지정 (MEMBER-02-01, MEMBER-05-01, MEMBER-06-01)
> - **약속 생성**
>   - 카카오톡 채팅방에 챗봇 초대 → 오픈빌더 스킬로 생성 요청 처리 → 고유 초대 링크 자동 발급
> - **참여**
>   - 회원 가입 없이 링크 접속만으로 참여, 동일 링크로 다수 참여 가능
>   - 다른 기기·브라우저에서는 닉네임·PIN으로 재인증 (MEMBER-04-02)
>   - 방장 설정이 끝나기 전(draft)에는 다른 사람의 참여를 허용하지 않는다 (MEMBER-03-02)
> - **시간 조율**
>   - 날짜 범위·하루 시간 범위 안에서 **30분 슬롯** 단위로 가능/불가능 선택 (TIME-06-01).
>   - 제출 후에도 마감 전까지 재제출 가능 (TIME-11-01). 마감은 **마감 시각 도달 또는 방장 조기 마감**으로만 이루어지며, **전원이 제출해도 자동 마감하지 않는다** (STATE-05-01, STATE-05-02, STATE-05-03)
> - **후보 추천**
>   - 약속 길이 **전체를 연속으로** 참석 가능한 인원만 해당 후보의 인원으로 계산 (RESULT-03-01)
>   - **가능 인원 많은 순 → 시작 시각 빠른 순**으로 정렬하고 상위 5개를 기본 표시 (RESULT-06-01, RESULT-06-02, RESULT-07-01)
>   - 가능 인원 **2명 미만 후보는 제외**. 방장 참석은 후보의 필수 조건이 아니다 (RESULT-04-01, RESULT-04-02)
> - **일정 확정**
>   - **자동 확정은 없다.** 마감 후 방장이 유효 후보 하나를 직접 선택해 확정한다 (RESULT-11-01)
>   - 확정 요청 시 서버가 후보 조건(미래 여부·범위·공통 가능 인원)을 재검증한다 (RESULT-12-01)
> - **약속 상태 관리**
>   - 상태: `draft` → `collecting` → `closed` → `confirmed`, 그리고 `cancelled` (STATE-01-01)
>   - **재설정**(collecting 중 설정 변경, 상태 유지) · **재조율**(closed·confirmed → collecting) · **취소**(방장만, 데이터는 보존) (STATE-01-02, STATE-09-01, STATE-10-01)
>   - 확정 결과는 링크 공유로 전달한다. 챗봇 자동 발송·알림톡은 MVP 이후
> - **참여자 관리**
>   - 본인 탈퇴, 방장의 참여자 내보내기, 방장 탈퇴 시 자동 승계 (MEMBER-10-01, MEMBER-10-02, MEMBER-12-04)

### v2 (MVP 이후 확장)

> 🧱 아래 항목은 비즈니스 규칙 DB · ERD(신버전) · API 명세서에 **아직 설계가 없다.** MVP 완료 후 규칙 → ERD → API 순으로 설계한 뒤 착수한다.

- **카카오 간편 로그인(회원)** — 현재 ERD는 전역 회원 테이블 없이 약속별 닉네임·PIN 구조이므로 스키마 확장이 선행되어야 한다
- **장소 투표 및 확정** — 투표로 장소를 확정하고 동률 시 방장이 최종 선택
- **위치 입력 및 중간지점 계산**
  - 참여자 추가 시 이동 시간 평균을 재계산하여 장소 정렬
- **장소 추천**
  - 네이버지도 API 기반
  - 카테고리 목록
  - 참여자 직접 후보 추가 가능
  - 우선순위: 카테고리, 구체적인 장소, 이동 시간
- 대중교통 소요시간 기반 정밀 중간지점 계산(ODsay)
- 약속 하루 전 알림 발송(알림톡)
  - 사업자 등록·메시지 템플릿 심사 필요, MVP 포함 여부 재검토 필요
- AI(LLM) 기반 투표·채팅 내용 분석
  - → 모임 목적/분위기 추론 후 장소 큐레이션
- 반복 모임 이력 관리, 정산 기능
- 예약 연동(캐치테이블 등 제휴)
- 길찾기
- **회원 전용 — 톡캘린더 연동**
  - 날짜, 시간이 확정되면 회원 참여자의 톡캘린더에 자동 등록 (장소는 선택 사항)
- **시간 조율 확장**
  - 날짜, 시간 블록 3단계 선택(가능해요/애매해요) — 현재 ERD는 슬롯 행의 존재 여부로 **가능/불가능 2단계**만 저장하므로 스키마 변경이 필요하다
  - 최소 인원 조건을 방장이 직접 설정하는 옵션 (MVP는 RESULT-04-01에 따라 2명 고정)

# 9. 가정 및 제약사항

**가정**

- 카카오 오픈빌더 스킬 서버 연동이 MVP 기간 중 정상 동작한다 (네이버지도 · ODsay는 MVP 이후 항목)
- MVP는 앱이 아닌 웹 기반 링크 공유형으로 운영한다

**제약사항**

- 약속 취소와 참여자 탈퇴는 상태 변경으로만 처리하고 데이터를 물리 삭제하지 않는다. 물리 삭제 예외는 draft(10분 만료, 방장의 draft 탈퇴)뿐이다. **기록 보관 기간은 STATE-11-02 미결**이므로 착수 전 결정이 필요하다
- 숫자 4자리 PIN은 조합이 10,000가지뿐이므로 해시 저장만으로는 부족하다. 시도 제한과 로깅 정책이 함께 필요하다
- (MVP 이후) 실시간 GPS 추적은 사용하지 않고 사용자가 직접 입력한 출발지만 사용하므로 위치정보법상 위험은 낮으나, 상세 주소가 개인 식별 정보와 결합되면 개인정보가 될 수 있어 역, 동, 랜드마크 단위 입력을 고려하고, 수집 목적 고지·최소 수집·모임 종료 후 삭제 정책이 필요함
- 비회원 참여 구조로 인한 스팸/투표 조작 방지를 위해 초대 토큰 검증, 요청 제한
- 카카오 오픈빌더 스킬 응답은 약 5초 제한 → 무거운 연산(장소 추천 등)은 스킬 응답 이후 웹에서 처리
- 카카오, 네이버가 유사 통합 기능을 언제든 추가할 수 있는 플랫폼 리스크 존재
- 장소 추천 데이터가 초기에는 부족해 추천 품질이 낮을 수 있음(카테고리 필터로 우선 보완)
