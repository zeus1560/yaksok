## 공통 계약 요약 (state.md STATE-API-09 3절)

1. **취소 우선:** 경로·필드 형식 → 약속 존재 → cancelled면 인증보다 먼저 409 `PROMISE_CANCELLED`
2. **인증:** 취소되지 않은 약속만 인증·소속·권한을 본다. 신규 참여·링크 조회에 기존 세션 검사를 적용하지 않는다
3. **effectiveStatus:** GET은 DB collecting + 마감 경과를 closed로 계산만 하고 쓰지 않는다
4. **잠금 후 재확인:** 쓰기는 잠금 후 약속 존재·취소·요청자 참여 상태·권한·마감·정원을 다시 본다. 인증이 실패한 요청은 DB를 바꾸지 않는다
5. **마감 경과:** 잠금 후 collecting 마감 도달이면 closed로 저장한 뒤 작업별 허용 상태를 본다
6. **잠금 순서:** 같은 약속 변경은 `promises` 행 잠금, 링크를 함께 잠그면 `promise_links → promises`

## 점검표

열 설명: **취소 판정**은 cancelled 약속을 어디서 거절하는지(세션보다 먼저인지), **Origin**은 Origin 검사 위치, **잠금**은 잠그는 행과 순서, **재확인**은 잠금 후(또는 읽기 트랜잭션 안) 세션·참여자·역할을 다시 읽는지, **마감 경과**는 collecting 마감이 지났을 때 closed 저장 여부와 응답, **허용 상태**는 성공하는 상태, **비활성 참여자**는 잠금 후(트랜잭션 안) 참여자가 cancelled이거나 세션이 사라진 경우의 응답, **쿠키**는 쿠키 갱신 방식, **no-store**는 모든 응답의 `Cache-Control: no-store`.

### 잠금 순서 정리 (공통 계약 6)

- `promise_links → promises`: 방장 등록(MEMBER-02), 설정 완료(STATE-02), 탈퇴(STATE-08). 셋 다 draft를 물리 삭제할 수 있는 경로다.
- `promises`만: 참여자 등록, 내보내기, 설정 변경, 마감, 확정, 재조율, 취소, 제출. 링크를 읽는 쿼리는 `FOR UPDATE OF p`로 약속 행만 잠근다.
- promises를 먼저 잡은 뒤 links를 잠그는 경로는 없다(R-28 점검과 같음).
- 잠금 없음: 링크 조회·발급, 로그인, 로그아웃, `/me`, GET 4개(REPEATABLE READ 읽기 트랜잭션).

### 마감 경과 시 closed 저장 (공통 계약 5, R-30 — 팀 결정 대기, 바꾸지 않음)

| 처리                         | API                                                                                  |
| ---------------------------- | ------------------------------------------------------------------------------------ |
| closed 저장 후 거절          | 제출(TIME-01, 409 `VOTING_CLOSED`), 설정 변경(STATE-03, 409 `INVALID_PROMISE_STATE`) |
| closed 저장 후 계속          | 마감(STATE-04), 확정(STATE-05), 재조율(STATE-06), 탈퇴(STATE-08)                     |
| **저장하지 않고 거절**       | 참여자 등록(MEMBER-03), 내보내기(MEMBER-08) — 둘 다 409 `DEADLINE_PASSED`            |
| 저장하지 않고 바로 cancelled | 취소(STATE-07) — 최종 상태가 cancelled라 중간 closed가 남지 않음(R-25)               |
| 저장 안 함(쓰기 아님)        | 로그인(MEMBER-04)·GET                                                                |

참여자 등록·내보내기가 closed를 저장하지 않아도 사용자 결과는 같다. GET(상태·현황·후보 조회)은 DB가 collecting이어도 마감 시각이 지났으면 closed로 계산해 응답하고(공통 계약 3), 그 뒤 들어오는 쓰기 요청(제출·설정 변경·마감·확정·재조율·탈퇴)이 잠금 후 같은 판정으로 closed를 저장한다. 달라지는 것은 DB의 `status` 값이 실제로 바뀌는 시점뿐이다. 다만 링크 조회(MEMBER-01)는 effectiveStatus를 계산하지 않는다(N-1).

## 이후 수정: 공통 인증의 취소 재확인 (fix 002, R-37, 2026-11-15)

- **문제:** 공통 인증 `lib/member/session-auth.ts`는 약속 상태를 읽은 뒤 쿠키 세션을 따로 읽는다. 그 사이에 취소가 커밋되면 취소가 만료시킨 세션 때문에 409 `PROMISE_CANCELLED` 대신 401 `UNAUTHENTICATED`가 나갔다(공통 계약 1 「취소 우선」이 동시 요청에서 어긋남). 032 미리보기 배포 확인 때 발견. 화면은 401 뒤 링크를 다시 조회해 취소 안내로 가므로 사용자 결과는 같았다
- **고친 뒤:** 세션이 무효(쿠키 없음·위조·만료·참여자 cancelled)해 401을 내기 직전에 약속 상태를 한 번 더 읽고, cancelled면 409 `PROMISE_CANCELLED`. 다시 읽은 약속이 없으면(만료 draft 삭제) 그대로 401
- **쿼리 수:** 401 경로에만 1번 늘고, 정상(200)·다른 약속 세션(403)·처음부터 cancelled(409) 경로는 그대로
- **적용 범위:** 공통 인증을 쓰는 세션 API 전부(위 표의 취소 판정 「세션보다 먼저 409」 행). **바꾸지 않은 것:** `/me`(MEMBER-05, `allowCancelled` — C-12 그대로 401), 로그아웃(MEMBER-07, 공통 인증 미사용 — R-31 그대로 204)
- 잠금 후·트랜잭션 안의 재확인은 원래 취소 409를 세션 401보다 먼저 보므로 바꾸지 않았다

## 재확인 방식 메모

- 쓰기 API의 잠금 후 재확인은 모두 같은 조건이다: 세션 행 없음 → 401·Max-Age=0, `expires_at ≤ 판정 시각`·참여자 cancelled·다른 약속·다른 참여자 → 401(다시 읽은 만료값으로 쿠키), 방장 전용이면 최신 role이 host가 아니면 403. STATE-02·TIME-01(둘 다 이번에 순서를 맞춤)·04·05·07·08이 각자 같은 코드를 갖고, 모두 잠금 후 취소 판정 바로 뒤에 재확인한다. STATE-03·06·MEMBER-08은 `lockPromiseAsHost`(`lib/state/settings-change.ts`)를 공유한다. 공통 함수로 묶는 것은 이번 범위 밖이다.
- GET 4개(STATE-01·10, MEMBER-06, TIME-02)는 REPEATABLE READ 트랜잭션 안에서 같은 조건으로 다시 읽는다. `/me`는 한 SQL 문장으로 다시 읽는다.
