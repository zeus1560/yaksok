| R-08 | 자동 확정 여부 (구 Q32) | **자동 확정 없음. 방장 수동 확정만** (R-02와 동일) |
| R-09 | 초대 링크 발급 API (구 A-08) | **MEMBER-API-09 `POST /api/v1/links`.** 웹은 링크만 발급하고 발급자를 방장 등록 화면으로 보낸다. 챗봇은 같은 내부 발급 함수를 호출한다. `promise_links.source`(web/kakao)로 출처를 기록한다 |
| R-10 | 방장 등록 API 세부 결정 (MEMBER-API-02, 2026-11-04) | **닉네임:** trim → **NFC 정규화** → `Intl.Segmenter` grapheme 단위 2~12자, `\p{Extended_Pictographic}` 포함 시 거절(MEMBER-05-01 권장안을 확정). `nickname`·`normalized_nickname` 모두 NFC 값. NFC 근거: MEMBER-API-04 로그인과 MEMBER-API-03 중복 판정이 닉네임 일치에 의존하므로, 입력 기기에 따라 조합형으로 들어온 같은 닉네임이 다른 값으로 저장되면 로그인 실패·중복 판정 오류가 생긴다. 방장 닉네임이 MEMBER-API-02에서 처음 저장되므로 여기서 도입했고, 03·04는 `lib/member/nickname.ts`의 `normalizeNickname`을 재사용한다. NFKC는 원문 보존·대소문자 구분 규칙과 충돌해 쓰지 않는다. **PIN 해시:** 명세의 bcrypt/argon2 대신 Node 내장 `crypto.scrypt`(**N=2^15**, r=8, p=1, maxmem 64MiB 명시, 16바이트 salt, `scrypt$N$r$p$salt$hash`). OWASP 최소값(N=2^17)에서 **의도적으로 낮췄다**: PIN은 1만 조합이라 해시 강도로는 유출 시 대입을 막지 못하고, N=2^17은 요청당 128MiB라 동시 요청 시 배포 인스턴스 메모리 부족과 MEMBER-API-04 로그인 반복을 통한 서비스 거부 위험이 있다. 실제 방어는 시도 제한(MEMBER-06-04 ❗미결)이 맡는다. 매개변수가 저장값에 남아 나중에 바꿔도 기존 해시를 검증할 수 있다. **draft 세션:** 발급 시각 + 24시간을 [제안]에서 확정(API_CONVENTIONS 5.2) |
| R-11 | 참여자 재인증 API 세부 결정 (MEMBER-API-04, 2026-11-04) | **로그인 가능 기간 = 링크 유효 기간(`linkExpiryBase + 7일`).** 지나면 410 `ACCESS_PERIOD_EXPIRED`, [제안]에서 확정. 근거: 세션 만료를 같은 기준으로 발급하므로 기간이 지난 뒤 로그인을 허용하면 즉시 만료된 세션을 주게 되고, 링크 조회(MEMBER-API-01)와 기준이 다르면 링크는 열리는데 로그인은 안 되는(또는 반대) 상태가 생긴다. 기준 시각은 API-01과 같은 함수로 고르므로 확정된 약속은 `confirmed_start_at` 기준이다. **draft 로그인:** 허용하며 세션은 발급 시각 + 24시간(R-10과 같음). 10분 지난 draft는 404(삭제는 MEMBER-API-02 몫). 근거: 방장 등록 응답 유실 시 재인증으로 복구하는 흐름(API_CONVENTIONS 6절)이 draft에서도 동작해야 한다. **판정 순서:** 약속 상태 판정을 PIN 검증보다 먼저 한다 — 취소·만료 약속에 PIN 대입 경로를 열지 않고 scrypt 비용도 쓰지 않는다. **에러 코드:** STATE 명세 기준으로 통일 — 취소된 약속 409 `PROMISE_CANCELLED`, 허용하지 않는 상태 409 `INVALID_PROMISE_STATE`(API_CONVENTIONS 3절의 `PROMISE_STATE` 폐기). **cancelled 참여자:** 로그인에서는 403 `PARTICIPANT_CANCELLED`(PIN 인증 성공 후 판정). 세션으로 인증하는 API는 401 `UNAUTHENTICATED`로 구분한다(C-07 안, 팀 확인 대기). **시도 제한:** 구현하지 않는다(2026-10-12 결정, 429 없음). **공개 배포 전 필수 재검토** — 실패 반환 지점을 한 곳으로 모아 두었다 |

## 3. 미결 규칙 전수 목록

### MEMBER (12)
`05-02` 닉네임 허용 문자 · `05-03` 공백 처리 · `05-04` 대소문자 · `06-02` PIN 분실 · `06-04` PIN 입력 실패 제한 · `07-01` 정원 설정 범위 · `07-03` 정원 축소 · `10-01` 탈퇴 가능 시점 · `10-02` 내보내기 권한 · `11-02` 강제 퇴장 후 재참여 · `12-02` 위임 수락 · `12-04` 마지막 방장 탈퇴

> **`06-04` PIN 입력 실패 제한은 공개 배포 전 필수 재검토 항목이다** (R-11). MVP 구현에는 없고 MEMBER-API-04의 실패 반환 지점 한 곳에 붙이도록 준비해 두었다.

> **닉네임 정규화가 선행 블로커다.** 05-02/03/04가 전부 비어 있는데 05-05는 "정규화한 닉네임으로 중복 판단, DB 유니크 제약"을 이미 확정했다. 정규화 정의 없이는 `normalized_nickname` 컬럼을 구현할 수 없다.

### STATE (6)
`07-01` 확정 가능한 상태 · `10-02` 취소 가능한 상태 · `10-03` 취소 복구 · `11-01` 약속 이후 조회 · `11-02` 기록 보관 기간 · `11-03` 기록 삭제

### TIME (24)
본문 공백 20개: `01-02` `03-01` `04-01` `04-02` `04-03` `05-01` `06-03` `07-01` `08-02` `09-03` `09-04` `13-01` `13-02` `13-03` `14-01` `14-02` `14-03` `14-04` `15-02` `15-03`
참조만 있고 자체 결정문 없음 4개: `02-02` `10-01` `15-01` `15-04`

> 날짜 범위(04-01~03)와 마감 입력(13-01~03), 마감 연장·단축(14-01~04)이 통째로 비어 있다. **STATE-03-01이 모집 시작 필수값으로 "날짜 범위·마감 시각"을 요구하는데 그 입력 규칙이 없다.**

### RESULT (16)
`02-01` `02-02` `05-01` `05-02` `05-03` `07-01` `07-02` `08-01` `08-02` `09-01` `09-02` `10-01` `11-02` `12-01` `12-02` `13-01`

> 단, **02-01·02-02·07-01의 답은 이미 다른 확정 규칙 본문에 들어 있다.** RESULT-03-01 "추가 결정"이 후보 시작 시각 30분 단위와 범위 초과 제외를, RESULT-06-01이 상위 5개 표시를 확정해 두었다. 구현은 가능하지만 정식 확정 처리를 안 하면 기준이 둘로 갈린다.

### EXCEPTION (22 / 23)
`13-01` 하나만 확정. 나머지 전부 미결.

## 4. 규칙 간 모순·참조 깨짐

| ID | 내용 |
| --- | --- |
| X-01 | **PIN 분실 복구 경로가 어디에도 없다.** MEMBER-09-02 → "04-01에서 정한다" → 04-01 → "06-02로" → 06-02 **공백**. 순환 참조 |
| X-02 | **MEMBER-04-02 ↔ 09-01 공중부양.** 04-02는 "PIN 변경 시 타 기기 로그아웃 여부는 09-01에서 정한다"는데, 09-01 본문은 "본인 정보 변경 불가" → PIN 변경 기능 자체가 없음 |
| X-03 | **MEMBER-11-01 페이지의 ID 오기.** 본문 머리말이 "MEMBER-11-03 / 재참여 제한"으로 적혀 있음. 05-06과 10-03이 "11-03 참고"라고 가리키지만 실제 11-03은 다른 항목. 참조가 전부 11-01을 향해야 맞음 |
| X-04 | **MEMBER-12-01 vs 12-02 전제 충돌.** 12-01은 자동 승계(방장이 대상을 고르지 않음), 12-02 항목명은 "위임 수락"으로 수동 위임 전제 |
| X-05 | **STATE-09-01 재조율 범위 축소.** STATE-01-01/01-02/06-03은 `closed·confirmed → collecting` 재조율을 전제하는데, 09-01 본문은 `confirmed`만 규정하고 closed는 "확인 필요"로 보류 |
| X-06 | **STATE-10-03(취소 복구) 미결인데 10-01이 "복원할 수 없다"고 이미 확정** |
| X-07 | **TIME-11-02 내부 모순.** "다시 제출하지 않고 마감되면 기존 제출값이 최종" vs 같은 페이지 마지막 줄 "재제출 필요한 사람이 안 하면 불가능으로 처리" |
| X-08 | **미제출자 표현 불일치.** TIME-10-03 "미응답으로 남는다" / TIME-12-02 "모든 시간 불가능으로 표시". TIME-10-04가 후자로 절충했으나 10-03 본문 미갱신 |
| X-09 | **RESULT-04-01 vs 13-02 공백.** 후보 조건은 2명 이상인데 13-02는 확정 후 2명 미만이 되어도 유지. "확정 **시점**에 2명 미만이면?"이 비어 있음 (12-01 재검증 규칙도 미결) |
| X-10 | **STATE-API-09 본문이 STATE-API-08의 복사본.** 제목·DB 설명은 "내부 공통 가드"인데 본문 1~4절이 08(본인 탈퇴)과 동일. 공통 가드 명세가 실제로는 없음 |
| X-11 | **STATE-API-08 처리 순서 번호 깨짐.** 3번 항목이 "이후 3번 이하는 실행하지 않는다"로 자기 자신을 가리킴. 9~11번이 말하는 "3·5·6번"은 실제 4·6·7번 |
| X-12 | **TIME 소관 중복 3건.** 미결인 TIME-05-01을 05-02가, 09-04를 09-01/09-02가, 15-03을 11-01이 이미 결정해 버림 |
| X-13 | **원문 결손.** TIME-11-01 마지막 문장이 "마감 후에는 수정할 수 없"에서 끊김. TIME-10-04에 "기준 버이" 오타. TIME-10-02의 규칙 ID 속성에 `<p>` 마크업 혼입 |

## 6. User Story 불일치

DB의 `릴리스` 속성은 v2 4개 영역을 모두 `후속`으로 두어 정면 충돌은 없다. 다만:

- **릴리스=MVP인데 본문 AC가 장소/출발지를 전제**: US-CREAT-04, US-AUTH-04, US-CONF-02, US-CONF-03, US-CONF-07, TECH-02
- **본문 「범위」 줄과 DB 속성값이 다름**: US-CREAT-01, US-AUTH-02, US-TIME-02, US-SCHED-05, US-ORIGIN-01/02, US-PLACE-03/04/05/06, US-SCHED-03

## 8. 착수 순서 제안

구현을 막는 블로커를 우선순위대로:

1. **닉네임 정규화 규칙** (MEMBER-05-02/03/04) — `normalized_nickname` 컬럼 구현 불가
2. **정원 범위** (MEMBER-07-01) — `participant_limit` CHECK 제약 작성 불가
3. ~~날짜 범위 3개월 vs 90일 (C-01)~~ — 해결됨 (R-07)
4. **마감 입력 규칙** (TIME-13-01/02/03, 14-01~04) — 모집 시작 필수값인데 입력 규칙 없음
5. **PIN 분실·실패 제한** (MEMBER-06-02/06-04) — 인증 구현 불가
6. **기록 보관 기간** (STATE-11-02) — 배포 전까지는 미뤄도 되나 개인정보 이슈
7. **카카오 챗봇 스킬 API 명세** (A-01) — MVP 필수
8. ~~초대 링크 발급 API 명세 (A-08)~~ — 해결됨 (R-09)

1~2번만 정해지면 **ERD 5개 테이블 마이그레이션은 착수 가능**하다. 4~5번은 STATE/MEMBER API 구현 직전에 필요하다.
