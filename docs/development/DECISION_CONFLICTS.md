| R-10 | 방장 등록 API 세부 결정 (MEMBER-API-02, 2026-11-04) | **닉네임:** trim → **NFC 정규화** → `Intl.Segmenter` grapheme 단위 2~12자, `\p{Extended_Pictographic}` 포함 시 거절(MEMBER-05-01 권장안을 확정). `nickname`·`normalized_nickname` 모두 NFC 값. NFC 근거: MEMBER-API-04 로그인과 MEMBER-API-03 중복 판정이 닉네임 일치에 의존하므로, 입력 기기에 따라 조합형으로 들어온 같은 닉네임이 다른 값으로 저장되면 로그인 실패·중복 판정 오류가 생긴다. 방장 닉네임이 MEMBER-API-02에서 처음 저장되므로 여기서 도입했고, 03·04는 `lib/member/nickname.ts`의 `normalizeNickname`을 재사용한다. NFKC는 원문 보존·대소문자 구분 규칙과 충돌해 쓰지 않는다. **PIN 해시:** 명세의 bcrypt/argon2 대신 Node 내장 `crypto.scrypt`(**N=2^15**, r=8, p=1, maxmem 64MiB 명시, 16바이트 salt, `scrypt$N$r$p$salt$hash`). OWASP 최소값(N=2^17)에서 **의도적으로 낮췄다**: PIN은 1만 조합이라 해시 강도로는 유출 시 대입을 막지 못하고, N=2^17은 요청당 128MiB라 동시 요청 시 배포 인스턴스 메모리 부족과 MEMBER-API-04 로그인 반복을 통한 서비스 거부 위험이 있다. 실제 방어는 시도 제한(MEMBER-06-04 ❗미결)이 맡는다. 매개변수가 저장값에 남아 나중에 바꿔도 기존 해시를 검증할 수 있다. **draft 세션:** 발급 시각 + 24시간을 [제안]에서 확정(API_CONVENTIONS 5.2) |
| R-11 | 참여자 재인증 API 세부 결정 (MEMBER-API-04, 2026-11-04) | **로그인 가능 기간 = 링크 유효 기간(`linkExpiryBase + 7일`).** 지나면 410 `ACCESS_PERIOD_EXPIRED`, [제안]에서 확정. 근거: 세션 만료를 같은 기준으로 발급하므로 기간이 지난 뒤 로그인을 허용하면 즉시 만료된 세션을 주게 되고, 링크 조회(MEMBER-API-01)와 기준이 다르면 링크는 열리는데 로그인은 안 되는(또는 반대) 상태가 생긴다. 기준 시각은 API-01과 같은 함수로 고르므로 확정된 약속은 `confirmed_start_at` 기준이다. **draft 로그인:** 허용하며 세션은 발급 시각 + 24시간(R-10과 같음). 10분 지난 draft는 ~~404~~ **410 `DRAFT_EXPIRED`**(2026-11-04 R-12에서 변경, 삭제 없음 — 삭제는 잠금을 잡는 MEMBER-API-02·STATE-API-02 몫). 근거: 방장 등록 응답 유실 시 재인증으로 복구하는 흐름(API_CONVENTIONS 6절)이 draft에서도 동작해야 한다. **판정 순서:** 약속 상태 판정을 PIN 검증보다 먼저 한다 — 취소·만료 약속에 PIN 대입 경로를 열지 않고 scrypt 비용도 쓰지 않는다. **에러 코드:** STATE 명세 기준으로 통일 — 취소된 약속 409 `PROMISE_CANCELLED`, 허용하지 않는 상태 409 `INVALID_PROMISE_STATE`(API_CONVENTIONS 3절의 `PROMISE_STATE` 폐기). **cancelled 참여자:** 로그인에서는 403 `PARTICIPANT_CANCELLED`(PIN 인증 성공 후 판정). 세션으로 인증하는 API는 401 `UNAUTHENTICATED`로 구분한다(C-07 안, 팀 확인 대기). **시도 제한:** 구현하지 않는다(2026-10-12 결정, 429 없음). **공개 배포 전 필수 재검토** — 실패 반환 지점을 한 곳으로 모아 두었다 |
| R-12 | 설정 완료와 모집 시작 API 세부 결정 (STATE-API-02, 2026-11-04) | **시작 날짜 하한 (신규 규칙, ⚠ STATE 담당자 구현과 비교 필요):** `startDate`는 잠금 후 판정 시각 기준 한국 시간 오늘 이후여야 한다(오늘 허용, 위반 시 422). STATE-03-01·ERD 4.2에는 없던 조건을 구현에서 새로 추가했다. 근거: TIME-API-01이 지난 슬롯을 무시하므로 과거 날짜는 선택할 수 없는 칸이 된다. 날짜 상한은 R-07 그대로 확정(요청서의 "시작일 + 89일" 안은 R-07과 충돌해 채택하지 않음). **만료 draft 코드 통일:** 약속(promiseId) 기준 API는 410 `DRAFT_EXPIRED`로 통일한다 — STATE-API-02는 잠금 후 삭제·커밋하고 응답, MEMBER-API-04는 잠그지 않으므로 삭제 없이 응답(R-11의 404를 변경). 링크(inviteToken) 기준 API(MEMBER-API-01)는 에러가 아니라 `unclaimed`·`draftExpired=true`로 응답한다(새 방장 등록 흐름으로 이어져야 하므로). **쿠키 갱신 규칙:** 세션 인증에 성공한 모든 응답은 DB `expires_at`까지 남은 초로 `Set-Cookie`를 다시 보낸다(API_CONVENTIONS 5절). 근거: draft 세션 쿠키는 Max-Age=86400으로 발급되는데, 모집 시작이 서버 세션을 `마감 + 7일`로 연장해도 브라우저 쿠키는 처음 받은 24시간 뒤 먼저 사라져 서버 세션이 살아 있는데도 재로그인이 필요해진다. 다른 기기의 쿠키도 다음 세션 인증 응답에서 따라잡는다. **promiseId 형식 오류:** 약속(promiseId) 기준 API는 모두 400 `INVALID_REQUEST`로 통일한다(STATE 명세 기준, MEMBER-API-04도 404에서 변경). 링크 토큰(inviteToken) 기준 API(MEMBER-API-01·02)는 기존대로 404 — 토큰은 접근 권한 자체라 형식 오류와 미존재를 구분하지 않는다. **상태 전환 컬럼:** DATABASE.md·스키마에 `status_changed_at` 등 전환 시각 컬럼이 없어 `status`와 설정 컬럼만 저장한다 |
| R-13 | 참여자 등록 API 세부 결정 (MEMBER-API-03, 2026-11-04) | **EXCEPTION-10-02 (중복 참여 요청):** 같은 닉네임 반복 등록은 409 `NICKNAME_TAKEN` 후 로그인(MEMBER-API-04)으로 복구한다. 이 약속의 유효한 세션(미만료 + active 참여자)을 가진 브라우저가 다른 닉네임으로 등록하면 409 `ALREADY_PARTICIPANT`. 쿠키가 없거나 무효·만료·cancelled 참여자의 세션이면 401 없이 등록을 진행한다(`session-auth.ts` 선택적 확인 모드). 한 브라우저를 여러 사람이 쓰는 경우는 다른 브라우저로 우회하는 것으로 감수한다. 다른 기기에서 다른 닉네임으로 재가입하는 것은 비회원 구조의 한계로 막지 않는다(ERD 9). **EXCEPTION-02-01 (마지막 정원 경쟁)·03-01 (동일 닉네임 경쟁):** `promises` 행 `FOR UPDATE` 잠금으로 직렬화되어 **먼저 커밋한 요청이 이긴다.** 나중 요청은 잠금 후 재조회에서 `PROMISE_FULL` 또는 `NICKNAME_TAKEN`을 받는다. `UNIQUE(promise_id, normalized_nickname)` 위반(P2002)도 `NICKNAME_TAKEN`으로 응답하는 최종 방어다. 개발 DB 병렬 요청으로 각각 201 1건·409 1건 확인. **검사 순서 변경 (닉네임 → 정원):** 명세의 정원 → 닉네임 순서를 바꿨다. 마지막 자리를 차지한 사람이 응답을 받지 못하고 같은 닉네임으로 재시도하면, 정원을 먼저 볼 경우 `PROMISE_FULL`을 받아 이미 등록됐다는 사실을 알 수 없고 로그인 복구(API_CONVENTIONS 6절)로 넘어가지 못한다. 어느 순서든 등록은 거절되므로 다른 요청의 결과는 바뀌지 않는다. **기타:** 취소된 약속 409 `PROMISE_CANCELLED`(R-11 통일), 10분 지난 draft 410 `DRAFT_EXPIRED`(삭제 없음, R-12 — 링크를 잠그지 않으므로), 마감 경과는 상태를 바꾸지 않고 409 `DEADLINE_PASSED`. 설정 값은 201 응답에 넣지 않고 조회 API에서 내려준다 |
| R-14 | 가능 시간 제출 API 에러 코드 정렬 (TIME-API-01, 2026-11-04) | **근거:** TIME 명세가 공통 규약(API_CONVENTIONS)보다 먼저 작성되어 같은 상황에 다른 이름을 쓰던 곳만 공통 코드로 맞추고, 입력 화면이 구분해 안내해야 하는 TIME 고유 코드(`VOTING_CLOSED`·`INVALID_SLOT_FORMAT`·`SLOT_LIMIT_EXCEEDED`·`AVAILABILITY_VERSION_CONFLICT`)는 유지한다. **변경:** 본문 형식 오류 422 `INVALID_REQUEST_BODY` → 400 `INVALID_REQUEST`, draft 409 `PROMISE_NOT_COLLECTING` → 409 `PROMISE_NOT_OPEN`, 10분 지난 draft 410 `DRAFT_EXPIRED`(삭제 없음, R-12·R-13) 추가, 다른 약속 세션 401 → 403 `FORBIDDEN`, 처리 순서를 세션 인증 모듈(`session-auth.ts`) 순서로 변경. **[제안] → 확정:** Origin 검증(403 `INVALID_ORIGIN`), 원본 slots 5,000개 상한(422 `SLOT_LIMIT_EXCEEDED`, A-05 해결), 본문 256KB 상한(413 `PAYLOAD_TOO_LARGE` 신설), 버전이 달라도 내용이 같고 제출 상태면 200을 주는 재시도 처리. **마감 전환:** collecting이고 마감이 지났으면 closed 전환을 커밋한 뒤 409 `VOTING_CLOSED` — 에러 응답이어도 전환은 롤백하지 않는다. **마감 코드 차이 (유지):** 같은 마감 경과 상황을 참여자 등록(MEMBER-API-03)은 409 `DEADLINE_PASSED`(DB 상태는 바꾸지 않음), 이 API는 409 `VOTING_CLOSED`로 낸다. 참여 화면은 "참여할 수 없음", 입력 화면은 "응답 마감"으로 용도가 달라 통일하지 않는다. **잠금 후 재확인:** 참여자 active·소속에 더해 세션 만료도 다시 본다(탈퇴·내보내기는 세션 `expires_at`을 현재 시각으로 바꾸므로). **슬롯 표기 통일:** 200 `slots`와 409 `AVAILABILITY_VERSION_CONFLICT` details `slots`를 모두 초 단위(`2026-10-28T14:00:00+09:00`)로 맞추고, TIME-API-02의 `availableSlots`·`me.slots`도 같은 형식을 쓴다. 밀리초 3자리는 `submittedAt`에만 쓴다. 근거: 같은 API에서 형식이 다르면 화면이 문자열 비교로 같은 시각을 다르게 본다(예: 충돌 details로 다시 그린 칸과 200 응답의 칸이 일치하지 않음). 슬롯은 30분 경계라 밀리초가 의미가 없다. **413 공통화:** `PAYLOAD_TOO_LARGE`를 API_CONVENTIONS 3절 공통 에러 코드에 추가했다. TIME-API-02의 draft 코드는 그 API 구현 때 정렬한다. **TIME-API-02 정렬 완료 (2026-11-05):** 처리 순서를 세션 인증 모듈 순서(400 → 404 → 409 `PROMISE_CANCELLED` → 401 → 403 `FORBIDDEN`)로, draft 409 `PROMISE_NOT_COLLECTING` → 409 `PROMISE_NOT_OPEN`, 10분 지난 draft 410 `DRAFT_EXPIRED`(조회라 삭제 없음) 추가, 다른 약속 세션 401 → 403, 에러 형식을 API_CONVENTIONS 3절로, 예시 `votingDeadlineAt`을 STATE-API-02와 같은 초 단위로 맞췄다. 상태별 허용 표의 `PROMISE_NOT_COLLECTING`도 모두 `PROMISE_NOT_OPEN`으로 바꿨다. ## 4. 규칙 간 모순·참조 깨짐

## 8. 착수 순서 제안

구현을 막는 블로커를 우선순위대로:

1. **닉네임 정규화 규칙** (MEMBER-05-02/03/04) — `normalized_nickname` 컬럼 구현 불가
2. **정원 범위** (MEMBER-07-01) — `participant_limit` CHECK 제약 작성 불가
3. ~~날짜 범위 3개월 vs 90일 (C-01)~~ — 해결됨 (R-07)
4. **마감 입력 규칙** (TIME-13-01/02/03, 14-01~04) — 모집 시작 필수값인데 입력 규칙 없음
5. **PIN 분실·실패 제한** (MEMBER-06-02/06-04) — 인증 구현 불가
6. **기록 보관 기간** (STATE-11-02) — 배포 전까지는 미뤄도 되나 개인정보 이슈
7. **카카오 챗봇 스킬 API 명세** (A-01) — MVP 필수
8. ~~초대 링크 발급 API 명세 (A-08)~~ — 해결됨 (R-09)

1~2번만 정해지면 **ERD 5개 테이블 마이그레이션은 착수 가능**하다. 4~5번은 STATE/MEMBER API 구현 직전에 필요하다.
