# STATE — 약속 상태 전환 비즈니스 규칙

> 원본: Notion 「비즈니스 규칙」 DB › 약속 상태 전환
> 추출일: 2026-10-30
> **이 문서는 구현의 1순위 기준이다. ERD·API 문서와 충돌하면 이 문서를 따른다.**
>
> 상태: `draft` → `collecting` → `closed` → `confirmed`, 그리고 `cancelled`

## STATE-01-01 — 상태 정의

- **검토 질문**: 각 상태가 의미하는 상황은 무엇인가?
- **상태**: 유지
- **결정**: 약속은 다음 다섯 가지 상태로 구분한다.
  - `draft`: 방장 설정이 완료되지 않은 상태
  - `collecting`: 참여자의 가능 시간을 수집하는 상태
  - `closed`: 응답을 마감했지만 일정을 확정하지 않은 상태
  - `confirmed`: 최종 일정을 확정한 상태
  - `cancelled`: 약속을 취소한 상태

  **예시**: 투표가 마감됐지만 방장이 시간을 선택하지 않았다면 `closed`이다.

  **추가 결정**: 상태별 세부 권한은 각 행동의 규칙에서 정한다.

  **재조율**: 방장이 응답을 다시 받기 위해 약속을 collecting으로 되돌리거나 다시 여는 것. 재조율할 때 설정을 함께 바꿀 수 있다.

  ① closed · confirmed에서 다시 응답을 받는 경우 → 재조율

  ② `collecting`에서 날짜 범위, 하루 시간 범위, 정원 증가, 마감 연장, 소요 시간 변경 → 재설정
- **원본**: https://app.notion.com/p/1367085f318283368a14017dd6b1c0a5

## STATE-01-02 — 허용 상태 전환

- **검토 질문**: 어떤 상태에서 어떤 상태로 이동할 수 있는가?
- **상태**: 유지
- **결정**: `draft → collecting`, `collecting → closed`, `closed → confirmed`, `closed·confirmed → collecting`(재조율)을 허용한다. 취소 전 상태에서는 방장이 직접 `cancelled`로 전환할 수 있다. 또한 방장이 탈퇴할 때 승계할 active 참여자가 없으면 약속을 자동으로 `cancelled`로 전환한다.

  **예시**: 확정된 약속을 다시 조율하면 `confirmed → collecting`으로 이동한다.

  **추가 결정**: `draft`에서의 설정 변경과 `collecting` 중 재설정(날짜·하루 시간 범위, 정원 증가, 마감 연장, 소요 시간 변경)은 재조율이 아니며, 상태도 바뀌지 않는다.

## STATE-02-01 — 초안 생성 시점

- **검토 질문**: 링크 생성과 방장 등록 중 언제 약속 초안을 생성하는가?
- **상태**: 유지
- **결정**: 링크 발급만으로 약속 초안(promise table)을 만들지 않는다. 해당 링크에서 **첫 참여자 등록이 성공할 때** 그 사람을 방장으로 지정하고 `draft` 약속을 생성한다.

  **추가 결정**: 나머지 요청은 등록하지 않고 "방장이 약속을 설정 중입니다" 화면으로 안내한다(참조: https://app.notion.com/p/2ed7085f31828281b581811d58a34184).
- **원본**: https://app.notion.com/p/5227085f318283e2b7b201884180d909

## STATE-02-02 — 미완성 초안 만료

- **검토 질문**: 설정이 완료되지 않은 초안을 얼마 동안 유지하는가?
- **상태**: 유지
- **결정**: 방장 등록 후 10분 안에 설정을 완료하지 못한 draft는 만료된다. GET 요청은 `created_at+10분`과 서버 현재 시각을 비교해 만료 여부만 계산하며 DB를 변경하지 않는다.

  만료 draft는 취소·탈퇴 데이터 보존 정책의 유일한 물리 삭제 예외다. 기존 방장 또는 새 방장의 쓰기 요청이 만료 draft를 발견하면 promise_link와 관련 행을 정해진 순서로 잠근 뒤 세션 → 방장 참여자 → promise 순서로 명시적으로 삭제한다. promise_link는 삭제하지 않고 미사용 상태로 되돌려 다음 사용자가 새 방장으로 등록할 수 있게 한다.

  **예시**: 방장 등록 후 10분이 지나면 기존 방장 화면에는 설정 시간이 만료되었다고 안내한다. 다음 등록 요청은 만료 draft를 정리한 후 같은 링크에 새 draft와 방장을 생성한다.

  **추가 결정**: 10분은 promises.created_at과 잠금 획득 후 서버 시각으로 판정한다. 설정 완료와 만료 정리가 경쟁하면 잠금 순서에 따라 먼저 유효하게 처리된 요청이 승리한다. 모든 FK는 ON DELETE RESTRICT이므로 자동 CASCADE를 사용하지 않는다.

## STATE-03-01 — 모집 시작 필수값

- **검토 질문**: 모집을 시작하려면 어떤 설정이 반드시 있어야 하는가?
- **상태**: 유지
- **결정**: 방장은 참여 정원, 선택할 날짜 범위, 매일 선택할 시각 범위, 약속 소요 시간, 응답 마감 시각을 설정해야 모집을 시작할 수 있다. 정원은 방장 포함 2~30명이다. 하루종일은 00:00~24:00으로 표현하며 종료 24:00을 허용한다.

  **예시**: 응답 마감 시각을 정하지 않으면 모집을 시작할 수 없다.

  **추가 결정**: 날짜 범위는 양끝을 포함해 최대 90일이며 서버 공통 제한값으로 적용한다. 일일 시작·종료는 API에서 HH:mm 문자열로 받고 서버에서 자정 기준 분 값으로 변환해 저장한다. 응답 마감 시각은 현재 시각 이후여야 하고, 날짜 범위의 마지막 날보다 앞서야 한다.
- **원본**: https://app.notion.com/p/4117085f318283b091c6818c654d42ca

## STATE-04-01 — 모집 중 변경 항목

- **검토 질문**: 모집 중에 방장이 바꿀 수 있는 설정은 무엇인가?
- **상태**: 유지
- **결정**: 모집 중 방장은 정원 증가, 마감 연장, **약속 소요 시간 변경**을 바로 할 수 있다. 소요 시간이 바뀌면 기존 입력으로 후보를 다시 계산한다. 날짜 범위·하루 시간 범위 변경은 모집 중 상태를 유지한 채 바로 적용하며, 기존 입력과 제출 상태는 STATE-09-03, 09-04를 따른다.

  **예시**: 소요 시간을 1시간에서 2시간으로 바꿔도 참여자의 입력과 제출 상태는 유지한다.

  **추가 결정**: 변경 후 소요 시간이 하루 선택 가능 시간보다 길어지는 설정은 허용하지 않는다.

## STATE-04-02 — 설정 변경 후 기존 입력

- **검토 질문**: 설정 변경으로 기존 입력이 유효하지 않게 되면 어떻게 처리하는가?
- **상태**: 유지
- **결정**: (참조: STATE-09-03 — https://app.notion.com/p/09e7085f318282c3b2bc019e07b0b9e6)

  약속 **소요 시간 변경은 기존에 입력해둔 가능 시간 입력을 변경하지 않는다.** 날짜·하루 시간 범위를 변경할 때만 새 범위를 벗어난 슬롯을 삭제하고, 범위 안의 슬롯은 유지한다.

  **예시**: 소요 시간을 늘려도 선택한 30분 슬롯은 그대로 남는다. 하루 종료 시각을 18:00으로 앞당기면 그 이후 슬롯은 삭제된다.

  **추가 결정**: 범위를 줄이면 범위 밖의 기존 입력이 삭제된다는 일반 경고를 변경 확정 전에 표시한다. 삭제되는 슬롯의 상세 목록이나 개수 미리보기 API는 제공하지 않는다.

## STATE-06-01 — 마감 후 참여 변경

- **검토 질문**: 마감 후 신규 참여·탈퇴·내보내기를 허용하는가?
- **상태**: 유지
- **결정**: (페이지 내 항목명: 마감·확정 후 참여 변경)

  마감 또는 확정 후에도 참여자 본인은 탈퇴할 수 있다. 방장의 참여자 내보내기는 재조율 중에만 허용한다.

  - `closed`에서 탈퇴하면 약속 상태는 유지하고, 탈퇴자를 제외하여 후보를 다시 계산한다.
  - `confirmed`에서 탈퇴하면 `confirmed_start_at`과 약속 상태를 유지하고 참석자 명단만 갱신한다.
  - 확정 일정에 참석 가능한 인원이 2명 미만이 되어도 자동으로 확정을 해제하거나 약속을 취소하지 않는다. 방장에게 인원 부족을 알리고 재조율 또는 취소를 선택하게 한다.
  - 탈퇴자는 `participants.status=cancelled`, `cancelled_at=현재 시각`으로 변경하고 모든 활성 인원·정원·후보·참석자 집계에서 제외한다. 관련 데이터는 자동 삭제하지 않는다.
  - 방장이 탈퇴하면 MEMBER-12-01·03·04의 자동 승계 규칙을 적용한다.

  **예시**: 3명이 참석하는 것으로 확정된 약속에서 1명이 탈퇴하더라도 확정 시간은 유지한다. 참석자 명단에서는 탈퇴자를 제외하고, 방장에게 참석 인원이 줄었음을 알린다.
- **원본**: https://app.notion.com/p/7697085f318282edbe95016924616fe4

## STATE-09-04 — 재설정 제출 유지

- **검토 질문**: 재설정할 때 기존 제출 상태를 유지하는가, 다시 제출하게 하는가?
- **상태**: 유지
- **결정**: 재조율이나 재설정으로 날짜 혹은 시간 범위의 바꿔 선택 가능한 날짜·시간이 하나라도 추가되면 기존 참여자의 제출 상태를 해제하고 새 범위를 확인한 뒤 다시 제출하게 한다. 범위가 **줄어들기만 하면** 범위 밖 입력을 삭제하고 제출 상태는 유지한다. 범위를 바꾸지 않은 재조율과 소요 시간만 변경해도 제출 상태를 유지한다.

  **예시**: 선택 종료일을 일요일에서 다음 주 일요일로 늘리면 재제출을 요청한다. 일요일에서 금요일로 줄이면 토·일 입력을 삭제하되 제출 완료 상태는 유지한다.

  **추가 결정**: 범위 축소로 본인의 입력이 삭제된 참여자에게 변경 사실을 알린다.

- **결정**: 확정된 약속에서 방장이 재조율을 시작하면, 기존 확정 날짜·시간을 **현재 확정 일정에서 해제**하고 약속 상태를 collecting으로 변경한다. 참여자의 가능 시간 입력은 이 작업만으로 삭제하지 않는다. 재조율을 다시 마감한 후 방장이 새 후보를 선택해야 새로운 현재 확정 일정이 생긴다.

## STATE-10-01 — 취소 권한

- **검토 질문**: 누가 약속을 취소할 수 있는가?
- **상태**: 유지
- **결정**: 현재 active 방장만 약속을 취소할 수 있다. 취소는 `promises.status=cancelled`, `promises.cancelled_at=현재 시각` 변경으로 처리하며 취소한 약속은 복원할 수 없다.

  약속 설정, 참여자, 닉네임, PIN 해시, 가능 시간, 제출 기록, `availability_version` 및 `confirmed_start_at`은 DB에서 삭제하지 않고 보존한다.

  해당 약속의 모든 참여자 세션은 행을 삭제하지 않고 `expires_at`을 현재 시각으로 변경하여 즉시 만료한다.

  취소된 약속의 화면과 API에서는 "취소된 약속입니다"라는 안내 외에 설정·참여자·입력·제출·확정 결과를 보여주지 않는다. 일반 STATE API는 세션 인증 결과보다 우선하여 `409 PROMISE_CANCELLED`를 반환한다.

  일반 참여자는 약속을 취소할 수 없으며 본인 탈퇴만 할 수 있다.

  **예시**: 방장이 취소한 뒤 기존 링크를 열면 "취소된 약속입니다"라고 표시한다. 이전 입력과 결과는 DB에 남지만 화면과 API에서는 조회할 수 없다.

  **추가 결정**: MVP에서는 취소 데이터를 자동 삭제하지 않는다. `cancelled_at`은 취소 시각 기록과 향후 보존 정책의 기준으로만 사용하며 취소 원인은 저장하지 않는다. 모든 FK는 ON DELETE RESTRICT을 사용한다.
- **원본**: https://app.notion.com/p/eee7085f3182832a855c0173117a62cd
